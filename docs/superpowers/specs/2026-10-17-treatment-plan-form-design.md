# Раздел «Планы»: письмо из Индии → план на формуляре Meditur HBG

Дата: 2026-10-17 · Статус: **принята к реализации** (п. 1 и 3 из §15 подтверждены владельцем, п. 2 — вариант по умолчанию) · Ветка: `treatment-plans`

> Здесь нет данных пациентов, врачей и клиник из реальных писем: примеры вымышленные.
> Репозиторий публичный, поэтому реальные письма и формуляры остаются только в вашей CRM.

## 1. Что делаем

Координатор получает ответ индийской стороны (письмо по-английски: текст или `.docx`) и сейчас вручную
превращает его в русский документ «ПЛАН МЕДИЦИНСКОГО ОБСЛЕДОВАНИЯ И ЛЕЧЕНИЯ» на формуляре Meditur HBG:
перевод, сжатие, сверка цен, вёрстка.

В боковом меню появляется раздел **«Планы»**. Координатор вставляет письмо, получает черновик плана,
правит его в редакторе рядом с превью PDF, отмечает «Проверено» и скачивает PDF для пациента.

Принципы (из них следует всё остальное):

1. **Источник истины — письмо.** Клиники, врачей, суммы, сроки и медицинские факты модель берёт только из письма
   (ваше решение «Только из письма»). Ничего не «дополняется из интернета».
2. **ИИ делает черновик, человек отвечает за результат.** Пока нет «Проверено» — PDF с водяным знаком «ЧЕРНОВИК».
3. **Макет — код, а не модель.** Модель отдаёт данные по строгой схеме, PDF всегда собирает наш код по одному формуляру.
4. **Каждая цифра прослеживается до письма:** у строки цены есть цитата-основание, плюс автоматические проверки.
5. **Как с PDF-досье:** PDF собирается «на лету» и нигде не хранится; в базе — исходное письмо и текст плана.

Не входит в первую версию (см. §14): PDF и фото на входе, отправка в WhatsApp, каталог клиник и «проверка по сайтам»,
таджикская версия, настройки блоков в интерфейсе, версии плана, экспорт в Word.

## 2. Сценарий работы

1. Меню → **Планы** → «Новый план».
2. Вставить текст письма или перетащить `.docx`; по желанию выбрать пациента из CRM (поиск по имени/телефону). «Сформировать».
3. Примерно через минуту («Читаю письмо…») открывается редактор: слева поля по разделам формуляра, справа PDF-превью
   с водяным знаком. Вверху панель **«Нужно проверить»** — предупреждения со ссылкой на поле.
4. Координатор правит. Сохранение автоматическое (через ~1,5 с после последней правки), превью обновляется.
5. «Отметить проверенным»: три подтверждения (суммы / врачи и клиники / имя и пол пациента) и ни одного красного
   предупреждения → водяной знак исчезает, фиксируется кто и когда.
6. «Скачать PDF» → `Plan_<Name>_<YYYY-MM-DD>.pdf`. Любая правка после проверки возвращает статус «Черновик».
7. Если ИИ недоступен или вернул мусор — кнопка «Заполнить вручную»: редактор и PDF работают как конструктор формуляра.

## 3. Рассмотренные подходы

| | Подход | Плюсы | Минусы |
|---|---|---|---|
| **A** (выбран) | Модель → строгий JSON → редактор → PDF собирает код | Формуляр всегда одинаковый; поля проверяются кодом; правится по полям; легко добавить таджикский и другие формы | Больше работы над интерфейсом редактора |
| B | Модель пишет готовый русский текст целиком → в PDF | Быстро сделать | Вёрстка «плавает»; нельзя автоматически сверить цены; правка — перепечатывание текста |
| C | Шаблон Word + LibreOffice → PDF | Шаблон правит нетехнический человек | На Render free (512 МБ) нет LibreOffice; таблицы с переменным числом строк хрупкие; нет живого превью |

Выбран **A**. Он же закрывает то, что в профессиональной практике считается обязательным: ИИ-черновик → проверка
другим человеком (в переводческом стандарте ISO 17100 «ревизия вторым лицом» — обязательная часть процесса),
а каждое извлечённое значение привязано к месту в источнике (так устроен Google LangExtract: «maps every extraction
to its exact location in the source text»).

## 4. Архитектура

```
письмо (текст / .docx)
   └─► prepareSource()  — .docx→текст, вырезать ссылки/контакты, нормализовать, посчитать sha256
        └─► Gemini, 1 вызов, ответ строго по JSON-схеме  ─► zod + sanitize ─► aiDraft
                                                                               │
 defaults (код): блоки формуляра, поддержка, рейсы, шаги ─► content ◄── правки координатора
                                                                               │
 runPlanChecks(content, источник, лид) ─► warnings  ◄───────────────────────────┤
                                                                               ▼
                                           buildPlanPdf(content, status) ─► PDF на лету (нигде не хранится)
```

Генерация идёт в фоне (как `lib/document-queue.ts`): запрос возвращается сразу, редактор опрашивает состояние.
Так длинный вызов модели не упирается в таймаут HTTP-запроса на Render, а перезапуск сервиса не теряет план
(зависшая генерация старше 5 минут считается неудавшейся, есть кнопка «Повторить»). Результат модели записывается,
только если генерация всё ещё та же (состояние `running` и тот же `startedAt`): поздний ответ после «Повторить»,
«Заполнить вручную» или чьих-то правок отбрасывается и ничего не затирает.

## 5. Данные

Коллекция `TreatmentPlans` (индексов в проекте нет и сейчас не нужны — записей будут сотни):

```ts
interface TreatmentPlanDoc {
  _id: ObjectId;
  leadId?: ObjectId | null;                 // привязка к пациенту CRM — необязательно
  version: number;                          // растёт при каждом сохранении; защита от затирания правок
  status: "empty" | "draft" | "reviewed";   // empty — письмо сохранено, плана ещё нет
  source: { text: string; kind: "paste" | "docx"; filename?: string; sha256: string };
  content?: PlanContent;                    // то, что правит координатор
  aiDraft?: PlanContent;                    // как вернула модель — для метрики «сколько правили»
  options: PlanOptions;
  warnings: PlanWarning[];                  // пересчитываются при каждом сохранении
  generation: { state: "idle" | "running" | "done" | "failed"; startedAt?: string; model?: string;
                promptVersion?: string; ms?: number; attempts?: number; error?: string };
  review?: { by: string; at: string; changedFields: number; confirmations: string[] };
  createdBy: string; createdAt: string; updatedAt: string;   // даты — ISO-строки, как в остальных коллекциях
}
```

Имя «кто» — то, что человек ввёл при входе (у CRM общий пароль и нет учётных записей), поэтому это не строгий аудит.

```ts
interface PlanWarning {
  code: string;                       // из таблицы §7
  level: "error" | "warn" | "info";   // красный / жёлтый / серый
  message: string;                    // по-русски, для координатора
  path?: string;                      // поле, к которому привязано: "costs.groups[0].rows[2].amount"
}
```

```ts
interface PlanContent {
  language: "ru";                                   // место под "tg" в будущем
  patient: { name: string; gender: "male" | "female" | "unknown" };
  profile: { specialty: string; condition: string };           // «Офтальмология» / «болезнь …»
  overview: string[];                                          // «МЕДИЦИНСКИЙ ОБЗОР», 1–6 пунктов
  diagnosis: { text: string; state: string; tactic: string; status: string };
  indiaSteps: string[];                                        // «ЧТО НЕОБХОДИМО СДЕЛАТЬ В ИНДИИ»
  tactic: { intro: string; items: { title: string; text: string }[] };
  documents: { title: string; items: string[] };               // пусто → раздела нет
  approach: { title: string; paragraphs: string[]; items: { title: string; text: string }[]; note: string };
  clinics: { id: string; name: string; shortName: string; city: string; area: string;
             doctor: string; why: string }[];
  costs: { groups: { title: string; note: string;
                     rows: { label: string; clinicId: string; amount: string; evidence: string }[] }[];
           footnote: string };
  stay: { rows: { label: string; value: string; total: boolean }[]; note: string };
  included: string[];                                          // «В СТОИМОСТЬ ЛЕЧЕНИЯ»
  notIncluded: string;
  letterIssues: string[];                                      // что модель заметила в письме; не печатается
  fixed: {                                                     // снимок из defaults.ts на момент создания
    tacticDisclaimer: string; costFootnote: string;
    flights: { enabled: boolean; from: string; to: string; text: string; checkedOn: string };
    support: string[]; nextSteps: string[];
  };
}

interface PlanOptions {
  date: string;                                    // ISO-дата плана, по умолчанию сегодня (Asia/Dushanbe)
  diagnosisHeading: "confirmed" | "by-documents";  // «ПОДТВЕРЖДЁННЫЙ ДИАГНОЗ» / «ДИАГНОЗ ПО ПРЕДОСТАВЛЕННЫМ ДОКУМЕНТАМ»
  clinicsVerifiedOnSites: boolean;                 // фраза «проверено по официальным сайтам клиник…»
  clinicsVerifiedMonth: string;                    // "2026-09", обязательна, если галочка стоит
  showPageNumbers: boolean;
}
```

Решения по данным:

- **Снимок блоков формуляра.** Тексты по умолчанию (поддержка Meditur HBG, дисклеймеры, рейсы, шаги) копируются в план
  при создании. Изменение шаблона позже не меняет уже проверенные планы.
- **Цена привязана к клинике по `clinicId`,** а подпись строки («Госпиталь А (Фаридабад)») собирает код из
  `shortName` + `city`. Переименовали клинику — подписи в ценах обновились; расхождение имён в списке и в таблице цен
  внутри письма перестаёт быть проблемой вёрстки.
- **`evidence`** — дословная цитата из письма для строки цены. В PDF не печатается, в редакторе показывается серым под
  полем суммы («Из письма: …») и проверяется кодом.
- Суммы — строкой («7 600 – 9 000», «+3 000 – 4 000», «80 – 90 / сеанс», «по запросу»); код приводит запись к единому виду
  (разряды неразрывным пробелом, диапазон через « – », без «USD»: валюта в шапке столбца) и умеет разбирать числа для
  проверок и сортировки.
- Необязательные разделы (`documents`, `approach`) — пустой массив/строка = раздела нет (без `null`, это проще для схемы Gemini).
- **Параллельные правки** (два человека, две вкладки, медленная модель). Три правила: (1) генерация записывает результат или
  ошибку, только если у плана всё ещё `generation.state = "running"` и тот же `startedAt`; (2) любая запись, меняющая `content`,
  `options` или `leadId`, идёт с фильтром по `version` — несовпадение даёт `409`, а не перезапись; (3) сохранение и «Заполнить
  вручную» переводят «зависшую» (старше 5 минут) генерацию в `failed` в той же записи. «Проверено» привязано к `version`,
  которую человек видел на экране.

## 6. Генерация

**Вход.** Текст до 40 000 символов (считается по вставленному тексту, до очистки; для `.docx` — по извлечённому); `.docx` до 5 МБ,
тело запроса до 6 МБ. `.docx` → `mammoth.convertToHtml` → простой текст (абзацы строками,
строки таблиц `A | B | C`: в сыром тексте mammoth ячейки превращаются в отдельные абзацы, и таблица цен теряет вид —
проверено на тестовом письме).

**`prepareSource`.** Нормализация переводов строк и пробелов; вырезаются URL, e-mail, телефоны, строки вида
«virtual tour via link»; исходный текст сохраняется как вставлен, а модель и проверки видят очищенный.

**Вызов модели.** Один вызов `generateWithFallback` (цепочка моделей и повторы уже есть), `temperature` 0.2,
`responseMimeType: application/json`, `responseSchema`, `propertyOrdering` (Gemini сохраняет порядок ключей из схемы).
Если API отклонил схему (HTTP 400, например как слишком сложную), тот же запрос повторяется на той же модели без `responseSchema`,
но с `responseMimeType: application/json` (флаг `keepGenerationConfig`): разбор и проверки те же, а свободный текст вместо JSON не запрашивается.
Из `PlanContent` модель заполняет всё, кроме `language` и `fixed` (их ставит код); `PlanOptions` модель не видит.

**Правила промпта (версия `PLAN_PROMPT_VERSION` пишется в план):**

1. Источник истины — только письмо. Нет в письме → пустая строка / пустой массив. Не добавлять врачей, клиники,
   суммы, сроки, медицинские факты и «общеизвестное».
2. Русский язык, спокойный деловой тон. Названия госпиталей и врачей — латиницей как в письме; города — по-русски.
   Аббревиатуры и процедуры (MIS-TLIF, ABO) — как в письме, с русским пояснением, если оно есть в письме.
3. Пол пациента (Mr./Ms., he/she) → «пациент»/«пациентка» и согласование по роду.
4. Убрать рекламу и самохвальство отправителя, приветствия, подпись, ссылки, контакты. «Мы / наша команда» из письма → «HBG».
5. Суммы переписывать дословно, валюта USD, ничего не пересчитывать и не складывать. Альтернативы по госпиталям — по одной
   строке на клинику со ссылкой на `clinicId`. Для каждой строки цены — дословная цитата `evidence`.
6. Если описание/ссылка в письме явно относится к другому госпиталю, названия в списке и в таблице цен различаются,
   числа или сроки противоречат друг другу — записать в `letterIssues` (одно предложение на проблему), не «исправлять» молча.
7. Никаких обещаний и гарантий результата; формулировки «возможно», «по предварительной оценке» сохранять.
8. Имя пациента: кириллицей по правилам транслитерации таджикских/узбекских имён; если неуверенно — латиницей как в письме.

**Разбор.** JSON → zod (лимиты длин: пункт обзора ≤ 400 символов, ячейка таблицы ≤ 300 и т. п.) → `sanitize` (ссылки, контакты,
приведение сумм). Ошибка → один повтор с перечнем нарушений в служебной пометке. Снова ошибка → `generation.state = "failed"`,
письмо сохранено, предлагаются «Повторить» и «Заполнить вручную».

**Привязка к пациенту.** Если выбран лид, имя пациента берётся из CRM; иначе имя предлагает модель и стоит предупреждение
«проверьте написание». Имя из письма сверяется с лидом (`compareNames` из `lib/documents.ts`) — письмо про другого человека
не должно попасть в чужую карточку.

## 7. Автопроверки (`runPlanChecks`)

Запускаются при каждом сохранении, дёшевы и детерминированы. Красные блокируют «Проверено», жёлтые — нет.

| Код | Уровень | Что проверяет |
|---|---|---|
| `money-missing` | красный | сумма из строки письма с USD/$ не найдена в плане (число сравнивается без пробелов и запятых: 6 800 = 6800) |
| `money-invented` | красный | сумма в плане не найдена в письме |
| `money-evidence` | красный | цитата-основание не найдена в письме или не содержит сумму строки |
| `price-unknown-clinic` | красный | у строки цены `clinicId` не из списка клиник |
| `name-mismatch` | красный | имя пациента в письме не совпадает с лидом |
| `contact-leak` | красный | в тексте плана остались URL, e-mail, телефон |
| `foreign-glyph` | красный | символы вне шрифта PDF (деванагари, арабица и т. п.) — в PDF стояли бы «квадраты» |
| `verified-month-missing` | красный | включена фраза «проверено по сайтам клиник», но не указан месяц |
| `sender-name` | жёлтый | в тексте плана есть название агентства-отправителя из переменной `PLAN_SENDER_NAMES` (через запятую; задаётся на Render, в репозитории не хранится; см. §15, п. 3) |
| `doctor-not-in-letter` | жёлтый | имя врача/клиники не нашлось в письме |
| `clinics-unverified` | жёлтый | врачи не проверены по сайтам клиник (пока не отмечено): в письме врач может быть указан неверно |
| `letter-issue` | жёлтый | всё, что модель записала в `letterIssues` |
| `flights-stale` | жёлтый | дата проверки рейсов пуста или старше 30 дней |
| `patient-name-translit` | жёлтый | имя пациента предложено моделью, не взято из CRM |
| `empty-section` | серый | нет клиник / цен / сроков пребывания |
| `long-cell` | серый | текст в ячейке слишком длинный для аккуратной таблицы |

Проверка чисел сознательно строгая только для денег. В «обзоре» модель может пересчитать («теряют 85–90 %» → «сохраняют
10–15 %»), поэтому остальные числа не блокируют.

Метрика качества: при «Проверено» считается `changedFields` — сколько полей координатор изменил относительно `aiDraft`.
Это честная оценка, насколько черновик хорош, и основа для правок промпта.

## 8. Редактор и превью

Страницы: `/dashboard/plans` (список: пациент, статус, дата, кто создал), `/dashboard/plans/new`, `/dashboard/plans/[id]`.

- **Слева** — аккордеон по разделам формуляра в порядке PDF. Строки/списки добавляются, удаляются, двигаются. В клиниках — кнопка
  «Цены по возрастанию» (порядок клиник в ваших формулярах не одинаков, поэтому по умолчанию — как в письме).
  Под суммой серым цитата «Из письма: …». Предупреждения — красные/жёлтые метки у полей и сводная панель сверху.
- **Справа** — настоящий PDF во встроенном просмотре (`iframe`, адрес `/api/plans/{id}/pdf?v={version}`). Это тот же код, что
  делает скачиваемый файл, поэтому превью не расходится с результатом. На телефоне — вкладки «Редактор / PDF».
- Автосохранение с задержкой; конфликт версий (`409`) → «План изменён другим пользователем — обновите».
- Во время генерации поля заблокированы, виден ход («Читаю письмо…»), опрос раз в 2 секунды.
- Переключатели: заголовок диагноза; «Проверил по сайтам клиник» + месяц; номера страниц; блок «Проезд» вкл/выкл.

## 9. Статусы и «Проверено»

`empty` → (генерация) → `draft` → («Отметить проверенным») → `reviewed`. Правка `reviewed`-плана возвращает его в `draft`.
Условия перехода: нет красных предупреждений (пересчитываются в момент нажатия), отмечены три подтверждения и `version` в запросе
совпадает с текущей — человек подтверждает ровно ту версию, которую видел на экране. Для `draft` скачивание разрешено (как «force» в
PDF-досье), но с водяным знаком «ЧЕРНОВИК» и суффиксом `_DRAFT` в имени файла.

Известное ограничение: PDF не хранится (как и досье). Содержимое проверенного плана и его блоки зафиксированы в базе, но после
обновления шаблона старый план при повторном скачивании получит новое оформление. Если понадобится хранить «ровно тот файл,
что ушёл пациенту», добавим сохранение PDF в момент «Проверено» (это отдельное решение про хранение медданных).

## 10. PDF-формуляр

Порядок разделов — как в трёх ваших примерах:

шапка (логотип · «МЕЖДУНАРОДНОЕ ЛЕЧЕНИЕ БЕЗ ПОСРЕДНИКОВ» · дата) → заголовок «ПЛАН МЕДИЦИНСКОГО ОБСЛЕДОВАНИЯ И ЛЕЧЕНИЯ» и подзаголовок →
полоса ПАЦИЕНТ / ПОЛ / ДАТА / ПРОФИЛЬ → МЕДИЦИНСКИЙ ОБЗОР → ДИАГНОЗ (таблица: диагноз, текущее состояние, потенциальная тактика,
текущий статус) → ЧТО НЕОБХОДИМО СДЕЛАТЬ В ИНДИИ (01, 02…) → ВОЗМОЖНАЯ ТАКТИКА ЛЕЧЕНИЯ + дисклеймер →
[НЕОБХОДИМЫЕ ДОКУМЕНТЫ] → [РЕКОМЕНДОВАННЫЕ КЛИНИКИ] → [ПРЕДЛАГАЕМЫЙ ПОДХОД] → ОРИЕНТИРОВОЧНАЯ СТОИМОСТЬ (группы таблиц) →
ПРОЕЗД И ПРЕБЫВАНИЕ → ЧТО ВКЛЮЧЕНО (две колонки) → СЛЕДУЮЩИЙ ШАГ (ПОДТВЕРЖДЕНИЕ → ПРИГЛАШЕНИЕ → ВИЗА → ПЕРЕЛЁТ → ИНДИЯ → ЛЕЧЕНИЕ) →
подвал на каждой странице. Разделы в скобках печатаются, только если заполнены.

Техника (всё проверено на пробном файле в pdfmake 0.3.11, уже есть в проекте):

- **Шрифт — DejaVu Sans**, как в ваших формулярах (они сделаны в LibreOffice с этим шрифтом). Четыре начертания лежат в
  `assets/fonts/dejavu/` (≈ 2,7 МБ, свободная лицензия Bitstream Vera — её текст рядом); кириллица, таджикские буквы ғ қ ҷ ӣ ӯ ҳ и
  знаки шаблона (— – • ± ≈ → №) в нём есть, тест сверяет каждый символ шаблона по файлам шрифта. PDF-досье остаётся на Roboto.
  Логотип подставляется как data-URI без сетевого доступа (как в `lib/dossier-pdf.ts`).
- **Заголовок раздела не остаётся одиноким внизу страницы:** каждый раздел — таблица, у которой заголовок раздела — строка-шапка
  (`headerRows`, `keepWithHeaderRows: 1`). При переносе таблицы на новую страницу заголовок и шапка столбцов повторяются.
  Простое правило «перенести заголовок, если дальше нет контента» в pdfmake 0.3 не работает (в «последующих узлах страницы» лежат
  и подвал, и ячейки следующей таблицы) — поэтому выбран структурный способ.
- Строки таблиц не рвутся по страницам (`dontBreakRows`); длинные текстовые блоки — рвутся по абзацам.
- Водяной знак «ЧЕРНОВИК» пока нет «Проверено».

**Блоки по умолчанию** (`lib/plans/defaults.ts`, взяты из ваших формуляров; копируются в план и правятся в нём):

- «Окончательное решение о тактике лечения принимается только после очного клинического и инструментального обследования пациента
  в Индии. Meditur HBG не гарантирует результат лечения.»
- «Итоговая стоимость лечения будет определена после первичной оценки в Индии и может измениться по результатам обследования.»
- ОРГАНИЗАЦИОННАЯ ПОДДЕРЖКА MEDITUR HBG: встреча и трансфер в аэропорту; личный координатор (кейс-менеджер) на протяжении всего
  пребывания; помощь в подборе проживания рядом с клиникой; помощь с обменом валюты.
- «Не включено: консультации, не входящие в согласованный план; продлённое пребывание; лечение прочих заболеваний, не связанных
  с текущим случаем» — только если в письме нет своего списка исключений.
- Рейс Душанбе → Дели: Somon Air SZ109, ≈ 2 ч 40 мин, ориентировочно 2 раза в неделю (пн, чт) + «подлежит уточнению перед бронированием».
- Шаги: ПОДТВЕРЖДЕНИЕ → ПРИГЛАШЕНИЕ → ВИЗА → ПЕРЕЛЁТ → ИНДИЯ → ЛЕЧЕНИЕ; «Чтобы продолжить, свяжитесь с вашим координатором Meditur HBG.»
- Фирменные строки (не в плане, а в коде): «МЕЖДУНАРОДНОЕ ЛЕЧЕНИЕ БЕЗ ПОСРЕДНИКОВ», адрес и WhatsApp в подвале.

**Чем PDF отличается от ваших формуляров и почему** (каждое отличие можно вернуть к вашему варианту):

1. Колонка «ПРОФИЛЬ» шире: у вас длинный диагноз превращается в столбец из 8–10 строк. Содержимое то же.
2. В подвале «стр. N из M» (переключатель).
3. «Информация о рейсах проверена …» печатается, только если задана дата; по умолчанию дата пуста.
4. «Врачи и госпитали указаны по итогам проверки … на официальных сайтах клиник (месяц год)» — только при включённой галочке
   «Проверил по сайтам клиник». Иначе честная формулировка: «Врачи и госпитали указаны по информации принимающей стороны.
   Итоговое заключение и состав лечащей команды определяются госпиталем после очной оценки пациента».

## 11. API

Все маршруты под общим входом (`middleware.ts` уже закрывает `/api/*`, кроме входа, вебхука и cron); входные данные — через zod.
Список пациентов для привязки — существующий `GET /api/leads?q=`.

| Метод и путь | Действие |
|---|---|
| `GET /api/plans` | список (без текста письма) |
| `POST /api/plans` | JSON `{ sourceText, leadId? }` или multipart (`file` `.docx`, `leadId?`) → создаёт план и запускает генерацию, `{ id }` |
| `GET /api/plans/[id]` | план, предупреждения, состояние генерации (для опроса) |
| `PATCH /api/plans/[id]` | `{ version, content?, options?, leadId? }` → сохранение + пересчёт проверок; `409` при конфликте версий или идущей генерации |
| `POST /api/plans/[id]/generate` | `{ overwrite?, manual? }`: повторная генерация (если есть правки — только с `overwrite: true`, иначе `409 has-edits`; идущая генерация — `409 running`) или `manual: true` — пустой план для ручного заполнения |
| `POST /api/plans/[id]/review` | `{ version, confirmations }` → `reviewed`, если версия — та, что человек видел, красных предупреждений нет (они пересчитываются) и отмечены три подтверждения; иначе `409` (`conflict` / `blocked` / `not-draft` / `running`) |
| `GET /api/plans/[id]/pdf` | PDF на лету (`inline`; `?download=1` — вложением) |
| `DELETE /api/plans/[id]` | удалить план вместе с письмом |

## 12. Безопасность и приватность

- Реальные письма, имена и диагнозы — только в вашей базе, как чаты и документы лидов. В репозиторий, тесты и промпт реальные данные
  не попадают; в промпте один **вымышленный** пример.
- Ссылки и контакты вырезаются до отправки в модель и проверяются после; в журналы пишутся id, длины, модель, время — не текст письма и не ФИО.
- Лимиты: 40 000 символов (по вставленному тексту, до очистки); тело запроса до 6 МБ; `.docx` до 5 МБ, и до распаковки по оглавлению
  архива проверяется суммарный размер содержимого (≤ 20 МБ) — защита от «zip-бомбы» на сервере с 512 МБ памяти.
- «Удалить план» стирает письмо и содержимое безвозвратно.
- Аудит «кто» — имя из формы входа (общий пароль), не учётная запись.

## 13. Тестирование и приёмка

Автотесты (вымышленные фикстуры, включая синтетический `.docx`, собранный скриптом):

- `schema`: примеры валидного/невалидного ответа; `source`: вырезание ссылок, таблица `.docx` → строки;
- `checks`: каждое правило — срабатывает и не срабатывает (в т. ч. 6 800 / 6800 / 6,800; письмо про другого человека);
- `pdf`: порядок и состав разделов, водяной знак, пустые разделы не печатаются, все символы шаблона есть в шрифте, PDF собирается и начинается с `%PDF`;
- API: создание → генерация (модель замокана) → правка → проверка → `reviewed` → правка возвращает `draft`; `409`; лимиты;
- чистая логика интерфейса: `ui.ts` (подписи статусов, раздел по пути предупреждения), `autosave.ts` (очередь автосохранения: слияние
  правок, версия из ответа, конфликт, повторы); пункт меню «Планы». Сами компоненты тестами не покрыты (в репозитории нет настройки
  тестов компонентов): их проверяют типы, линтер, `next build` и дымовой прогон в браузере. Прогон: `tsc`, `lint`, `jest`, `next build`.

**Что я не могу проверить отсюда: качество ответа Gemini** (ключа в моей среде нет). Поэтому приёмка такая: после выкладки вы прогоняете
свои три письма и сравниваете с вашими формулярами; присылаете расхождения; я правлю промпт и пример. Заранее я прогоню весь конвейер
**кроме модели** на ваших трёх письмах (черновик набираю сам по схеме, только у себя в песочнице): проверю вёрстку и автопроверки на
реальных текстах и пришлю PDF для сравнения с вашими.

## 15. Решения

1. **Контакты в подвале — подтверждено.** «WhatsApp (+992) 00 550 77 77» настоящий номер; хранится в `lib/plans/defaults.ts`.
2. **Название раздела с диагнозом.** «ПОДТВЕРЖДЁННЫЙ ДИАГНОЗ» — название раздела формуляра, из письма оно не берётся (из письма берётся
   только текст диагноза). В той же таблице строка «Диагноз предварительный…» противоречит слову «подтверждённый», поэтому в редакторе
   есть переключатель на «ДИАГНОЗ ПО ПРЕДОСТАВЛЕННЫМ ДОКУМЕНТАМ». По умолчанию — ваше название.
3. **«HBG» и отправитель — подтверждено.** В плане нет названия агентства-отправителя, ссылок на его сайт и личной подписи; действующее
   лицо везде «HBG»: «мы» из письма → «HBG». Сайт агентства со временем может измениться, поэтому ничего не привязано к его адресу:
   вырезаются любые ссылки, а название агентства задаётся в `PLAN_SENDER_NAMES` на Render (через запятую) и меняется без правки кода;
   упоминание такого названия в плане даёт жёлтое предупреждение `sender-name` (не блокирует).
4. **Блок «Проезд»:** рейс Somon Air SZ109 (пн, чт) — значение по умолчанию из ваших формуляров, дата «проверено» пуста,
   пока не заполните; через 30 дней — жёлтое предупреждение.
5. **Порядок клиник** — как в письме (у вас он иногда отличается), двигается вручную.
6. **Там, где ваши формуляры добавляют собственные рекомендации** (например, «Семье предстоит решить, интересен ли вариант…»),
   модель этого не придумывает — только то, что есть в письме. Такие строки добавляются вручную.
7. **Срока действия цен** в формулярах и письмах нет — не добавляю; при желании добавим поле.
8. **Шрифт PDF — DejaVu Sans** (как в ваших формулярах), а не Roboto: так вёрстка ближе к вашим образцам и в шрифте есть все
   нужные знаки. Досье пациента остаётся на Roboto. Сменить шрифт позже — заменить четыре файла и имя семейства в `lib/pdf-fonts.ts`.
