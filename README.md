# Meditur HBG CRM

WhatsApp-CRM для координации лечения пациентов из Центральной Азии в Индии.
Задеплоено: https://meditur.onrender.com

## Запуск

```bash
npm install
cp .env.example .env.local   # заполните MONGODB_URI и NEXTAUTH_SECRET как минимум
npm run dev
```

Откройте http://localhost:3000 — редирект на `/login`.

Вход — по общему паролю из переменной `DEMO_COORDINATOR_PASSWORD` (`.env.local` локально,
Environment на Render). Любой, кто введёт правильный пароль, попадает в CRM; поле «имя» необязательное.
Если переменная не задана, вход закрыт. После 5 неверных попыток с одного IP вход блокируется на 15 минут.

### Первый запуск с реальной MongoDB

```bash
# Реальные 15 лидов из текущей таблицы координатора (на 23.09.2026)
node --env-file=.env.local scripts/import-leads.mjs

# ИЛИ вымышленный демо-набор (для стенда/теста, не для прод-базы)
node --env-file=.env.local scripts/seed.mjs
```

Оба ничего не делают, если в `Leads` уже что-то есть (кроме `--force`).

## Документы пациента и PDF-досье

Карточка пациента → «Документы пациента». Фото и PDF (с телефона, либо уже присланные пациентом
в WhatsApp — кнопка «Фото из переписки»; PDF от пациента сохраняются автоматически со статусом
«не разобран») разбираются Gemini **один раз на файл**: тип (`report` — заключения/анализы,
`imaging` — сами снимки МРТ/КТ/рентген, `other` — прочее), расшифровка оригинала и перевод на
английский. Результат хранится в коллекции `Documents`, и дальше используется как текст.

- **Экономия токенов.** `/api/leads/[id]/case-assistant` больше не прикладывает разобранные фото
  картинкой на каждую реплику — вместо них идёт блок с переводами (`lib/dossier.ts`).
- **Очередь на сервере** (`lib/document-queue.ts`): один документ за раз, статус в Mongo, зависшие
  после рестарта сервиса подхватываются снова (очередь поднимается при открытии карточки).
- **Проверки** (`lib/documents.ts`): числа из оригинала должны быть в переводе; имя на документе
  сверяется с лидом (кириллица ↔ латиница); неразборчивые места помечаются. Предупреждения видны
  в панели. Номера ИНН/паспорта/телефоны/адреса в перевод не переносятся (см. промпт, правило 6).
- **PDF** (`/api/leads/[id]/dossier`) собирается на лету через `pdfmake` без браузера (на free-инстансе
  Render Chromium не помещается по памяти) и нигде не хранится. Оригиналы фото в PDF не вшиваются —
  они пересылаются отдельными фото. Если есть непроверенные документы, UI спросит подтверждение.
- Документы лежат отдельно от `MediaAssets`: кнопки очистки хранилища их не трогают — удаляйте
  документы кнопкой «корзина» в панели.
- Промпт разбора — `lib/document-extraction-prompt.ts`.

## Планы лечения

Раздел «Планы» (`/dashboard/plans`): из письма агентства-отправителя получается формуляр «План медицинского обследования и лечения» (PDF).

- **Сценарий.** «Новый план» → вставить текст письма или загрузить `.docx` (до 5 МБ) → Gemini разбирает письмо один раз и
  возвращает черновик (в фоне, страница опрашивает статус каждые 2 с; при ошибке — «Повторить» или «Заполнить вручную») →
  редактор: слева разделы в порядке PDF, справа превью PDF (на телефоне вкладки «Редактор / PDF») → автопроверки дают
  красные, жёлтые и серые предупреждения → «Отметить проверенным» (нужны три подтверждения: суммы, клиники, пациент; красных
  предупреждений быть не должно) → «Скачать PDF». Черновик скачивается с водяным знаком «ЧЕРНОВИК» и суффиксом `_DRAFT`.
  Любая правка проверенного плана возвращает его в «Черновик».
- **Код.** `components/plans/*` (редактор и блоки), `lib/plans/*` (схема, промпт, проверки, автосохранение, PDF),
  `app/api/plans/**`. Лимиты длин и схема — `lib/plans/schema.ts`.
- **`PLAN_SENDER_NAMES`** — необязательная переменная окружения: названия агентства-отправителя через запятую. Если такое
  название попало в текст плана, появляется жёлтое предупреждение `sender-name`. В репозитории значений нет: укажите их в
  окружении сервиса (Render), а не в коде.
- **Ограничения.**
  - PDF не хранится: он собирается заново при каждом открытии и скачивании. Проверенный план хранит содержимое в базе, но после
    обновления шаблона старый план получит новое оформление.
  - Поле «кто» (автор, кто отметил «Проверено») — имя, введённое при входе. Общий вход без учётных записей, поэтому это не строгий аудит.
  - Качество разбора Gemini проверяется на реальных письмах перед использованием: тестовые данные не отражают все формулировки агентств.
  - В журналах пишутся только идентификаторы, длины, модель, время и коды ошибок; текст письма и ФИО в журналы не попадают.

## Instagram: автоответ в комментариях и директе

Бот отвечает от имени профессионального аккаунта Meditur HBG и приглашает продолжить разговор в WhatsApp:
**+992 00 550 77 77** (ссылка https://wa.me/992005507777). Ответы без ИИ: фиксированные шаблоны из `lib/instagram/replies.ts`
(русский или английский — по языку комментария или сообщения).

- **Новый комментарий под постом** → публичный ответ под комментарием (только номер) и личное сообщение (Direct) автору с номером
  и ссылкой wa.me. Ответы на ответы, свои комментарии и комментарии из одних эмодзи бот пропускает.
- **Личное сообщение в Direct** → приглашение в WhatsApp.
- **Молчание там, где уже писали.** Если в Direct этому человеку уже писал сотрудник или сам бот, приглашение и личный ответ
  не отправляются в течение `INSTAGRAM_DM_COOLDOWN_HOURS`. Публичный ответ под комментарием при этом выходит.
- **Защита от повторов.** Каждое событие обрабатывается один раз. Публичный ответ одному человеку — не чаще раза в
  `INSTAGRAM_COMMENT_COOLDOWN_HOURS`. Перед ответом бот делает паузу, как живой человек (`INSTAGRAM_REPLY_DELAY=off` убирает паузы).
- **Выключить** можно без удаления настроек: `INSTAGRAM_AUTOREPLY=off`. Вебхуки при этом принимаются, но ничего не отправляется.
- **Код.** `lib/instagram/*` (настройки, разбор вебхука, шаблоны, Graph API, хранилище, обработка событий),
  `app/api/instagram-webhook/route.ts` (приёмник вебхуков), `app/api/settings/instagram/route.ts` (статус для настроек).
  В MongoDB: коллекции `InstagramEvents` (дедупликация), `InstagramContacts` (cooldown), `InstagramAuth` (продлённый токен).
- **Журналы** содержат только идентификаторы, причины и коды ошибок. Тексты комментариев и сообщений и токены в журналы не попадают.

**Настройка (один раз)**

1. Meta for Developers → ваше приложение → Instagram → «API setup with Instagram business login».
2. Шаг «Generate access tokens»: добавьте профессиональный аккаунт Instagram и сгенерируйте токен → в Render переменная
   `INSTAGRAM_ACCESS_TOKEN`. Токен живёт 60 дней, бот продлевает его сам.
3. Там же, рядом с Instagram app ID, — Instagram app secret → `INSTAGRAM_APP_SECRET` (по нему проверяется подпись вебхуков).
4. Придумайте строку для проверки адреса → `INSTAGRAM_VERIFY_TOKEN`. Она должна совпадать с полем «Verify token» в консоли.
5. Перезапустите сервис на Render (redeploy), чтобы переменные подхватились.
6. Шаг «Configure webhooks»: Callback URL `https://<домен CRM>/api/instagram-webhook`, тот же verify token, «Verify and save»,
   затем подпишите поля `comments` и `messages`.
7. Переведите приложение в режим Live (App settings → Basic: Meta обычно просит URL политики конфиденциальности).
   В режиме Development вебхуки приходят только от аккаунтов, которые имеют роль в приложении.
8. Проверка: войдите в CRM и откройте `/api/settings/instagram` — там видно имя аккаунта и подписанные поля.
   Если поля пустые, откройте `/api/settings/instagram?subscribe=1`.
9. Проверка работы: оставьте комментарий с другого аккаунта. Публичный ответ появится примерно через минуту, затем придёт
   личное сообщение. Напишите аккаунту в Direct — придёт приглашение в WhatsApp.

**Ограничения.**

- В некоторых конфигурациях Meta требует App Review (расширенный доступ). Без него вебхуки и ответы могут работать только для
  аккаунтов с ролью в приложении.
- Отвечать можно только тем, кто оставил комментарий или первым написал в Direct. Это правила Instagram, обойти их нельзя.
- Бот не ведёт переписку: он только приглашает в WhatsApp, дальше разговор ведёт координатор.

## Установка как приложение (PWA)

CRM устанавливается на телефон и компьютер как обычное приложение с логотипом Meditur HBG.
Нужен HTTPS (на Render он есть).

- **Android / Chrome / Edge:** кнопка «Установить приложение» (иконка загрузки) в шапке CRM либо пункт меню браузера «Установить приложение».
- **iPhone / iPad:** Safari → «Поделиться» → «На экран «Домой»» (кнопка в шапке покажет эту подсказку).

Состав: `app/manifest.ts` (манифест), `public/sw.js` (service worker), `public/offline.html` (страница без сети),
`public/icons/*` + `app/apple-icon.png` + `app/favicon.ico` (иконки), `public/brand/*` (логотип с прозрачным фоном).
Service worker **ничего не кэширует**, кроме страницы «Нет соединения»: данные пациентов на устройстве не оседают.
Обновили логотип — замените файлы в `public/icons`, `public/brand`, `app/` (размеры: 192, 512, maskable 512, apple 180).

## Пайплайн лидов

Синхронизирован с реальной таблицей координатора
(`Meditur-Учёт_лидов.xlsx`, лист «Дашборд»), а не с исходным архитектурным
планом — он в проде оказался подробнее:

Новый → Первый контакт → Консультация назначена → Консультация проведена →
Смета отправлена → Ожидание решения → Выиграно / Отказ

## Что реализовано

- **Layout и авторизация** — NextAuth (Credentials), защищённые
  `/dashboard/*` через middleware, боковое меню, тёмная/светлая тема.
- **Воронка лидов** (`/dashboard`) — KPI-плашки сверху (всего лидов, в
  работе, просрочено касание, выиграно, конверсия — автоматический аналог
  ручного листа «Дашборд»), канбан на `@dnd-kit` с 8 колонками выше.
- **Таблица лидов** (`/dashboard/leads`) — `@tanstack/react-table`,
  поиск/фильтр по статусу с фильтрацией на сервере.
- **Карточка пациента** (`/dashboard/leads/[id]`) — анамнез, переписка с
  «Остановить/Возобновить ИИ», этап + причина отказа (когда «Отказ»),
  источник/кампания/город, свободные заметки координатора (автосохранение),
  генерация Medical Opinion Request.
- **MongoDB Atlas** (`lib/db.ts`) — коллекции `Leads`, `Messages`, база
  `meditur`. Поля лида расширены под реальную таблицу: `source`, `campaign`,
  `homeLocation`, `declinedReason`, `notes` — их не было в исходном плане.
- **`/api/whatsapp-webhook`** — приём сообщений и фото от Evolution API,
  находит/заводит лид по номеру, стейт-машина на `aiPaused`, ответ через
  Gemini уходит пациенту обратно через `POST /message/sendText/{instance}`.
- **`lib/playbook.ts`** — настоящий регламент Meditur HBG для ИИ (не
  заглушка): как говорить о диагнозе и ценах, отработка возражений
  («дорого», «подумаю», «посоветуюсь с семьёй», «вдруг мошенники» и т.д.),
  визовые факты, чек-лист «чего никогда не говорить». Адаптирован из
  «Медитур — Гид для координатора» (изначально скрипт звонков) под формат
  переписки в WhatsApp. Обновляйте этот файл, если гайд поменяется.

## Важные технические заметки

- **Gemini.** В исходном плане — «Gemini 1.5 Flash», но поколения 1.0/1.5
  полностью отключены Google (404). По умолчанию `gemini-3.8-flash`, имя
  вынесено в `GEMINI_MODEL` — линейка обновляется быстро, сверяйтесь с
  https://ai.google.dev/gemini-api/docs/deprecations.
- **Evolution API.** `POST /message/sendText/{instance}` — плоское тело
  `{ number, text }` (без `textMessage`/`options`, которые встречаются в
  старых примерах и ломают запрос на текущих версиях). Вебхук в Evolution
  укажите на `POST https://meditur.onrender.com/api/whatsapp-webhook`,
  событие `MESSAGES_UPSERT`.
- **Ответ бота: паузы, письмо, звонок.**
  - Пузыри одного ответа уходят по очереди: паузу (время «печатает…» +
    1–2 сек) выдерживает сам сервер (`interBubblePauseMs` в
    `lib/humanize.ts`), а не только параметр `delay` Evolution.
  - Перед первым пузырём бот отмечает сообщения пациента прочитанными
    (`POST /chat/markMessageAsRead/{instance}`, Evolution API 2.3.7), через
    0,4–1,2 сек начинает «печатает…» (параметр `delay` у `sendText` сам
    показывает набор текста — отдельный `sendPresence` не нужен). Только если
    бот реально отвечает; сбой «прочитано» ответ не задерживает.
    Выключается `WHATSAPP_MARK_READ=off`.
  - Страховка от «воды» без лишних токенов (`lib/humanize.ts`): пузырь длиннее
    240 символов режется по предложениям на 2+ сообщения (они уходят с
    паузами, всего не больше 4), а «!» оставляется один на весь ответ —
    остальные становятся точками. Причина: в реальных переписках до правок
    медиана ответа была ~205 символов, каждый пятый — длиннее 300, «!» стоял в
    47% пузырей.
  - Контекст переписки (`askGemini`): бот видит всю историю лида (без служебных
    пометок и недоставленных ответов), но без дат — поэтому (а) сообщения
    координатора идут в модель как служебная пометка «координатор написал
    пациенту», а не как слова пациента; (б) если с последнего сообщения прошло
    больше суток, к новому сообщению пациента дописывается подсказка «вернулся
    через N дней — поприветствуй и продолжи, не начинай заново»
    (`lib/return-gap.ts`; системный промпт и его кэш не меняются).
    Старые фото/голосовые видны модели только как заглушки, а документы из
    раздела «Документы» и поля карточки лида в контекст бота не попадают.
  - Арабская/персидская графика в ответе бота запрещена: такой ответ
    возвращается модели на переписывание (до 2 раз), а если не помогло —
    пузырь не отправляется, ИИ ставится на паузу с пометкой для координатора.
  - В рабочее окно (по умолчанию 12:00–17:00 по Душанбе, см. `BOT_TIMEZONE`,
    `CALL_WINDOW_START_HOUR`, `CALL_WINDOW_END_HOUR`) к последнему сообщению
    пациента дописывается короткая подсказка «позови на звонок»
    (`lib/call-window.ts`). Системный промпт при этом не меняется — иначе
    сбрасывался бы его кэш в Gemini.
  - Статистика реальных переписок: открыть, будучи залогиненным,
    `/api/settings/chat-analysis?days=30` (или `?since=<ISO-дата>` — «после
    выкладки правок»). Только числа: длина ответов, доля «воды» и повторов,
    паузы между пузырями, арабская графика, часы обращений (`byHour` — сообщения,
    `leadsByHour` — разные пациенты), зовёт ли бот на звонок в окне. Ни текстов, ни имён, ни номеров в ответе нет.
- **Render free tier.** Инстанс засыпает после ~15 минут без запросов и
  просыпается 30–60 сек на первый запрос — для вебхука в реальном времени
  это может ощущаться как задержка первого ответа пациенту. Если это
  станет проблемой — либо платный инстанс на Render, либо перенос на тот
  же VPS, где уже крутится Evolution API.

- **`lib/follow-up.ts` + `/api/cron/follow-up`** — автоматическая каденция
  follow-up из гайда (День 0/1/2–3/5–7/10–14). День 0 уходит сразу при
  переводе лида в «Смета отправлена»; дальше эндпоинт нужно дёргать раз в
  день внешним планировщиком (Render Cron Job или бесплатный
  https://cron-job.org) на
  `GET https://meditur.onrender.com/api/cron/follow-up?secret=<CRON_SECRET>`.
  Если 10–14 дней нет ответа — эндпоинт сам ставит ИИ на паузу и помечает
  лид как требующий координатора, ничего лишнего пациенту не шлёт.

## Что ещё не автоматизировано

- **Content Caching** для системного промпта Gemini (снижение стоимости
  токенов) — из исходного плана, пока промпт отправляется каждый раз целиком.
- Follow-up-сообщения на шагах 1/2–3/5–7 — фиксированные шаблоны из гайда, а
  не персонализированные Gemini-черновики (сознательно — надёжнее для
  автоматической рассылки без просмотра координатором перед отправкой).
